# Pinecone Vector Data Model

## Why a Vector Database

Traditional keyword search is useful when a query shares exact words with a paper title or abstract. Research discovery often needs semantic matching instead: a query about "small memory LLM deployment" should find work about quantization, pruning, parameter-efficient fine tuning, and efficient inference even when those exact words differ.

Pinecone stores vector embeddings and retrieves nearby records by similarity. In this project, Pinecone integrated embedding generates vectors from paper text on the server, so the application only sends plain text records and natural-language queries.

## Core Objects

- **Index**: The top-level Pinecone database resource. This project uses one index, defaulting to `aiml-paper-search`.
- **Namespace**: A logical partition inside the index. The default namespace is `arxiv-papers`, allowing test or alternate datasets to live separately.
- **Record ID**: A stable identifier such as `arxiv:1706.03762`. It uniquely addresses one paper record.
- **Embedded text**: The combined title and abstract stored in the configured text field, defaulting to `paper_text`.
- **Vector**: The numeric representation generated by Pinecone's hosted embedding model. The code does not hard-code dimensions because the integrated model determines them.
- **Metadata**: Filterable fields stored with the vector, including title, abstract, authors, published year, primary category, all categories, URL, and source.

## Search vs Relational Lookup

A relational lookup retrieves rows that match exact predicates. A keyword engine ranks documents using tokens and term statistics. A vector database ranks records by geometric similarity between embeddings, which is better suited for natural-language meaning. This project combines vector similarity with metadata filters so a user can ask a broad semantic question while narrowing by category and publication year.
